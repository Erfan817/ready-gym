# Ready Gym：Agent as Foundation 设计

状态：架构理念与设计，非实现承诺。本文把 agent 从「产品的一个模块」升维为「产品的地基」，与已有文档衔接，不推翻它们。

## 0. 本文解决什么问题

现有文档把 agent 定位成「内嵌 Agent」——产品的一个功能模块（项目规划.md 的「可视化入口＋内嵌 agent」）。这是**给旧软件打补丁**的思路：先有人体点选、计划、记录这些功能，再把一个 chatbot 塞进去当助手。

本文换一个地基：**agent 不是模块，agent 就是产品本身的地基/中枢**。人体模型、动作库、计划引擎、训练记录、知识库，全部降级为 agent 可以调用的「能力」。人不再操作工具，而是下指令、拿结果。

## 1. 定位的转变

| | 旧定位（可视化入口 + 内嵌 agent） | 新定位（agent as foundation） |
|---|---|---|
| 用户角色 | 操作员：点人体、填表单、翻计划 | 下指令者：说目标、说约束、说反馈 |
| agent 角色 | 辅助功能，回答问题 | 产品中枢，编排一切工具 |
| 入口 | 人体模型是主入口，agent 是侧栏 | 教练对话是主入口，人体模型是 agent 的一个工具 |
| 判断句 | 「点选肌群，生成适合自己条件的计划」 | 「像有个教练，你说目标它自己排、自己调」 |

判据来自用户原话的直觉：**「我希望一打开就是 AI 问我基本信息，而不是我来选」**。这句话本身就是 agent-first 的判断标准：用户要的是「下指令」，不是「操作工具」。

## 2. 三层架构（地基视角）

```text
意图层   用户说自然语言：目标、条件、约束、反馈
          ↓
中枢层   Agent 编排循环：理解意图 → 决定调哪个工具 → 校验结果 → 回复/追问
          ↓
能力层   人体模型 · 动作库 · 计划引擎 · 训练记录 · 知识库 · 会员额度
          ↓
数据层   PostgreSQL 业务表（Java 唯一写入者）· pgvector 知识向量
```

核心翻转：传统是「界面 → 功能 → 数据」，agent-first 是「agent → 工具 → 数据」。

- **界面只是 agent 的嘴巴和眼睛**（聊天框渲染 agent 的话，卡片渲染工具结果）。
- **工具才是 agent 的手**（读档案、查动作、出计划、记日志、检索知识）。
- **agent 编排循环是地基**：没有它，上面的能力只是散落的 API；有了它，用户一句话就能跨多个能力拿到结果。

## 3. 每个「原功能」如何变成 agent 的工具

| 原功能（模块视角） | 变成 agent 的工具（地基视角） |
|---|---|
| 人体肌群点选 | `select_muscles`：agent 按用户意图主动调用；人体 SVG 保留为「快捷输入」而非必经流程 |
| 动作库 | `search_exercises`：按肌群/器械/难度检索 |
| 计划引擎 | `propose_plan` / `propose_revision`：规则校验底座，agent 出草稿 |
| 训练记录 | `get_training_history` / `log_set`：读写本人日志 |
| 视频知识库 | `search_knowledge`：RAG 检索审核资料，附来源 |
| 会员额度 | `check_entitlement`：agent 调工具前先查额度 |

关键：工具不消失，只是**从「人点按钮触发」变成「agent 按需调用」**。人体点选这类可视化能力不删，而是退成一种可选输入方式——新手看不懂专业术语时，点一下人体比打字快；但高手直接说「我想练背和腿」更快。

## 4. 交互范式：意图 → 编排 → 工具 → 结果 → 确认

- 传统（固定路径）：表单 → 提交 → 规则引擎 → 展示。路径写死，加一种新场景就要改界面。
- agent-first（按需编排）：用户在对话里表达，agent 决定这轮要调哪个工具、要追问什么、要出什么结果。

两者共有的不变项：**结果必须人确认后才落库**。agent-first 只改变「路径由谁决定」，不改变「写入权在谁手里」。

示例（一镜到底）：

```
用户：21 岁，175/70，想增肌，有哑铃，每周三次
agent → 调 get_profile 建档工具 → 缺「训练经验/安全自述」 → 追问
用户：没受过伤，练过半年
agent → 校验完整 → 出摘要卡 → 用户确认
agent → 调 propose_plan（规则底座） → 展示一周安排 + 替代动作
用户：周三没空，改成四天
agent → 调 propose_revision → 出差异 → 用户确认 → 保存新版本
```

全程用户没有「点人体 → 选器械 → 提交」这条固定路径，但每一步结果都经过用户确认。

## 5. 边界：地基越核心，越不能失控

agent 当地基不等于无限自治。**恰恰相反，agent 越靠中心，越要收紧它的手。** 沿用并强化现有文档的安全边界：

- **agent 只提案，Java 是唯一写入者**：计划与日志的落库由 Java 服务执行，agent 不直接碰生产库、不执行任意代码。
- **高风险反馈分流**：胸痛、头晕、急性损伤、持续关节疼痛 → 停止训练建议并提示专业评估，不进入正常加量/换动作流程。
- **失败可回退**：模型超时/失败时回退到审核过的规则模板计划，并明确标记「回退」，不假装个性化生成。
- **工具参数全校验**：动作 ID 必须在审核动作库存在，器械必须符合用户条件，数值阈值由规则配置和专业评审定，不由模型自定。
- **知识文本是数据不是指令**：检索出的「执行某命令」等内容不能改变工具权限。

这些约束在 agent-first 下比在「内嵌 chatbot」下更重要：内嵌 bot 失控只影响一个侧栏，地基失控影响整个产品。

## 6. 与现有代码/文档的衔接

不是推倒重来，现有工作已经是 agent-first 的第一步：

| 已有资产 | 在 agent-first 里的位置 |
|---|---|
| `android/CoachChatScreen.kt` + `CoachClient.kt` | 意图层 + 界面层：教练对话入口 |
| `agent-python/`（intake 服务） | 中枢层的第一个编排：建档问询（get_profile 工具） |
| `docs/conversation-first-ai.md` | agent-first 的「建档」阶段决策 |
| `技术栈.md` 第 4 节 | 中枢层实现方式：SDK/HTTP 客户端＋显式工具注册＋有上限编排循环，不强制 LangChain |
| `项目规划.md` | 业务边界与安全约束（第 5 节 Agent 行为设计）继续有效 |

下一步衔接：把「计划生成」也做成 agent 的工具调用（`propose_plan`），而不是独立于对话的表单流。当前 intake 已经打通「对话 → 工具 → 确认」，计划阶段复用同一套循环即可。

## 7. 里程碑重心（沿用项目规划分阶段，标注 agent-first 重心）

- **A 需求验证**：验证「教练对话」是不是用户真正想要的入口（而不是人体点选）。
- **B 业务闭环**：先把**工具层**做扎实——规则底座、动作库、记录、档案。地基的「手」必须先可靠，再谈「脑子」。
- **C 接入 agent 中枢**：agent 接上工具，跑通「意图 → 编排 → 工具 → 确认」闭环，含超时回退。
- **D 试用迭代**：收集「agent 哪句话没用、哪次编排错了」的真实反馈。
- **E 付费验证**：会员额度做成 agent 的工具前置检查。

顺序不变，重心从「先做界面」移到「先做可靠的工具层，再接中枢」。

## 8. 给简历/面试的一句话

> Ready Gym 是一个 agent-first 的健身产品：agent 是产品中枢而非附加功能，人体模型、动作库、计划引擎、训练记录都作为 agent 可调用的工具存在；Java 管业务写入与权限，Python 管 agent 编排与工具调度，agent 只提案、用户确认后才落库。

这句话能讲清三件事：架构理念（agent-first）、工程边界（Java/Python 分工、写入权）、安全设计（提案/确认分离）——正是实习面试里比「我做了个健身 App」值钱的地方。
